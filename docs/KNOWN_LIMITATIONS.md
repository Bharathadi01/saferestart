# SafeRestart — Known Limitations & Operational Boundaries

To maintain technical integrity and scientific credibility for judges, operators, and evaluating engineers, this document discloses all known limitations, operational assumptions, and architectural boundaries of the current SafeRestart prototype.

---

## 1. Prototype Scope & Regulatory Limitations

- **Decision-Support Only**: SafeRestart is an operational decision-support tool designed to coordinate field evidence and structure supervisor approvals. It **does not certify drinking-water microbiological safety**.
- **No Replacement for Statutory Testing**: SafeRestart cannot and does not replace statutory municipal drinking-water release requirements, such as certified 24-hour membrane filtration or enzyme-substrate tests for *Escherichia coli* and total coliforms.
- **Demonstration Thresholds**: Configured demonstration parameters (e.g., free chlorine residual $\ge 0.20\text{ mg/L}$, minimum distribution pressure $\ge 20.0\text{ psi}$, turbidity $\le 1.0\text{ NTU}$, flushing duration $\ge 15\text{ minutes}$) represent common engineering baseline values for demonstration and must be tailored to jurisdiction-specific water quality regulations (e.g., WHO guidelines, US EPA Safe Drinking Water Act, or BIS 10500 standards).

---

## 2. Telemetry & Simulation Boundaries

- **Synthetic Telemetry**: All time-series telemetry (pressure transducers, bulk flow electromagnetic meters, free chlorine colorimeters, turbidity sensors) displayed in the application is generated by a deterministic mathematical simulation model. It does not represent live municipal SCADA infrastructure.
- **Simplified Hydraulic Modeling**: The network graph provides topological connectivity (reservoirs, valves, junctions, pipes, hydrants) for operational context. It does not run a continuous dynamic hydraulic differential equation solver (such as EPANET or Infoworks WS Pro) in the browser canvas.

## 3. Persistence & Cloud Infrastructure Status

- **Phase 2 Local Persistence**: In the current local development build, data is managed by [`LocalSafeRestartAdapter`](file:///Users/bharathadithya/.gemini/antigravity/scratch/saferestart/src/lib/adapters/local-store-adapter.ts) in memory. Restarting the local Node.js process resets state to the deterministic initial baseline.
- **Target Cloud Implementation**: An infrastructure-as-code template ([`template.yaml`](file:///Users/bharathadithya/.gemini/antigravity/scratch/saferestart/template.yaml)) is provided for AWS SAM deployment (Amazon DynamoDB tables, EventBridge event bus, and S3 evidence bucket). These resources have not been provisioned in the live cloud during this local evaluation phase.
- **Simulated S3 URI References**: Field photograph attachments in the current local mode use simulated URI references (`s3://saferestart-evidence/photos/...`) rather than live multi-part S3 pre-signed upload URLs.

---

## 4. Artificial Intelligence & Generative Models

- **Decision Gating Strictness**: Large language models (Amazon Bedrock or local heuristic synthesis) are strictly restricted to advisory synthesis, operator note structuring, and directive formatting. Generative AI is architecturally prohibited from approving service restoration, clearing a HOLD, or modifying state machine transitions.
- **Local Fallback Heuristics**: When AWS credentials or Bedrock models are not actively configured in `.env.local`, the application falls back to a deterministic rule-based engineering explainer. No remote API call is attempted without configured credentials.

---

## 5. Security & Multi-Tenancy

- **Role Attribution**: In the local development prototype, operator and supervisor roles (e.g., `Distribution Operations Supervisor`, `Chief Water Works Engineer`, `Field Technician`) are selectable through the UI to demonstrate role-based state machine gating. In production, this requires Amazon Cognito User Pools with cryptographic JWT claims and AWS WAF protection.
- **Single-Tenant Scope**: The current database and store structure models a single municipal utility authority across five District Metered Areas (DMAs). Multi-utility partitioning requires tenant ID scoping in DynamoDB partition keys.
